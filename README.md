# lemmego/apptest

Boots a **real** Lemmego application in a test and drives it over HTTP,
without binding a port.

```go
func TestAProfileIsPublic(t *testing.T) {
    a := apptest.New(t,
        apptest.WithConfig(configs.All()),
        apptest.WithProviders(bootstrap.LoadProviders()...),
        apptest.WithRoutes(bootstrap.LoadRoutes()...),
        apptest.WithScratchDB(),
    )

    a.Get("/@grace").Send().
        AssertStatus(200).
        AssertHeadContains(`<title>Grace Hopper`)
}
```

## The one idea worth understanding

**The application under test is the application that ships.**

`New` goes through `app.Configure()` and `engine.Handler()` — the same
sequence `Run` performs before it starts listening. Providers run, application
and HTTP middleware install, routes mount, the session wrapper goes on. A
harness that reassembled those pieces itself would drift from production, and
a test that passes against a drifted harness is worse than no test.

It fails the test rather than returning an error: a harness that cannot boot
has nothing useful to say, and threading an error through every call site buys
nothing.

## Install

```bash
go get github.com/lemmego/apptest
```

## Options

| Option | Effect |
|---|---|
| `WithConfig(configs.All())` | The real configuration map |
| `WithProviders(...)` | Pass `bootstrap.LoadProviders()...` for the real stack, or a subset to isolate one concern |
| `WithRoutes(...)` | Pass `bootstrap.LoadRoutes()...` |
| `WithMiddlewares(...)` | Application middleware |
| `WithHTTPMiddlewares(...)` | `net/http`-level middleware |
| `WithErrMap(...)` | So a test sees the statuses and pages the application really returns |
| `WithScratchDB()` | A scratch database, migrated, then dropped |
| `WithScratchDBNoMigrate()` | For testing the migrator itself |
| `WithStrictSSR()` | A failed server-side render becomes a 500 |
| `WithoutCSRFToken()` | Send unsafe requests with no token, to assert the protection exists |
| `WithSharedCache()` | Opt out of per-App cache isolation |
| `WithWorkingDir(dir)` / `WithoutChdir()` | Override the chdir to the project root |

Without `WithConfig` the application gets only the minimum needed to boot,
which is enough for routing tests and nothing else.

## Requests

```go
a.Get("/launchpad")
a.Post("/launch").JSON(map[string]any{"title": "A thing"})
a.Put("/profile").Form(map[string]string{"headline": "Building things"})
a.Patch(path).Raw(body).Header("Content-Type", writer.FormDataContentType())
a.Delete("/launch/x")

a.Get("/feed").Inertia().ActingAs("42").Send()
```

`Raw` is what a multipart upload needs: the boundary is part of the
Content-Type and is generated by `multipart.Writer`, so neither `JSON` nor
`Form` can express one.

Cookies are carried across requests on one `App`, so a login followed by a
page load behaves as a browser would.

## `ActingAs` resolves a real user

```go
a.Get("/settings").ActingAs("42").Send()
```

It sets a header, which a middleware installed **only by this package** turns
into a verified subject via `auth.SetSubject`. So the application's own
`UserLoader` runs and the handler receives the same concrete `*models.User` it
would in production.

That is the whole point: a fabricated user would make every test of
`auth.UserAs[*models.User]` vacuous. It is a header rather than a boot option
because authentication is a property of a request, not of an application, and
one `App` serves many requests.

The id is whatever `UserProvider.GetID` returns — a string, even when the
column is an integer.

## CSRF and the Inertia version are handled, and neither is a bypass

**CSRF.** The harness presents the token on unsafe requests the way a browser
does. The token is session-backed: the middleware compares what the request
presents against what the session holds, so a request can only satisfy it by
having first obtained a session — exactly the property CSRF protection exists
to assert. A handler that forgot to be behind the middleware is still caught.
Where no token exists yet, one is obtained by a `GET`, because a browser
cannot post a form it never loaded either.

Use `WithoutCSRFToken()` to assert on the rejection itself. A test that only
ever sends a valid token cannot tell a guarded route from an unguarded one.

**The Inertia asset version** is discovered once per `App` and sent
automatically. This is not optional: Inertia's version protocol answers **409
Conflict** whenever the version a client sends differs from the server's, and
a request sending none differs from any non-empty version. An application that
hashes its Vite manifest — the default — would otherwise answer 409 to every
Inertia request, and the test would be asserting on an empty body.

`InertiaVersion(v)` overrides it, for a test deliberately exercising the
mismatch.

## Assertions

```go
resp := a.Get("/launch/a-thing").Send()

resp.AssertStatus(200).
    AssertHeader("Content-Type", "text/html; charset=utf-8").
    AssertSee("A thing").
    AssertDontSee("draft").
    AssertHeadContains(`<title>A thing`, `"@type":"SoftwareApplication"`).
    AssertServerRendered()

a.Post("/launch").JSON(body).Send().
    AssertStatus(302).
    AssertRedirect("/launch/a-thing").
    AssertCookie("lemmego_session")

a.Get("/api/me").JSON(nil).Send().
    AssertJSONPath("user.handle", "grace").
    AssertJSONPathAbsent("user.password")
```

`AssertHeadContains` looks **only in `<head>`**, which is the difference
between asserting that a title tag exists and asserting that the string
appears anywhere on the page.

`AssertJSONPathAbsent` is the one to reach for when the test is "this field
must not be published" — a leaderboard with no score, a match with no contact
details.

`JSONValue(path)` returns the raw value for an assertion this package does not
model.

## A database per test

`WithScratchDB()` creates a uniquely named database **on the server the
application is already configured to use**, points the configuration at it,
runs every migration registered with `migration.GetMigrator`, and drops it
when the test ends. Tests do not see each other's rows and can run in any
order.

Under a test binary that configuration comes from `.env.test`, which
`api/config` loads *instead of* `.env` — so a suite points itself at a test
database by having the file, not by remembering a variable.

```ini
# .env.test
DB_CONNECTION=postgres
DB_HOST=localhost
DB_PORT=5432
DB_USERNAME=you
DB_DATABASE=postgres
DB_PARAMS=sslmode=disable
```

**There is no apptest-specific environment variable**, and that is deliberate.
There used to be one, and the trouble with asking twice is that the two
answers can differ: it supplied host, user, password and port but not options,
so a managed URL's `sslmode=require` survived into a local server and every
test died with `pq: SSL is not enabled on the server`. One source cannot
disagree with itself.

**It fails rather than skipping.** The previous version skipped when its
variable was unset, so that `go test ./...` would not fail for somebody with
no server running. The price was a suite reporting `ok` in 1.3 seconds having
skipped 448 tests and run 7 — a pass indistinguishable from a real one except
by the clock. A test that needs a database and has none has not passed.

Scratch databases are implemented for Postgres only. An application configured
for another engine is told so, rather than being handed a connection error.

A scratch database per test is deliberately heavier than a transaction rolled
back at the end. It is also the only thing that tells the truth about a
migration, a trigger, a generated column or a deferred constraint, which is
most of what is worth testing at this layer.

`Ctx()` is the test's own context for seeding a fixture or asserting against a
row afterwards. It is cancelled when the test ends, so a query left running by
a failed assertion does not outlive it.

### Interrupting the run drops the database too

Ctrl-C out of a suite and `t.Cleanup` never runs — a signal terminates the
process, which is [golang/go#41891](https://github.com/golang/go/issues/41891)
and not something a test can register its way out of. So the first test to
create a scratch database also installs a SIGINT and SIGTERM handler that
drops whatever is live, writes what it dropped to stderr, and then re-raises
the signal so the exit status is the conventional one.

The handler restores the default signal disposition *before* it starts
dropping, so a second Ctrl-C kills the process immediately. That ordering is
the point: a leaked database costs a few megabytes, where a cleanup holding
the only handler while it waits on a database server nobody can reach is a
test run that cannot be stopped.

It is installed on first use rather than in an `init()`, so a harness used
without `WithScratchDB` never touches the process's signal disposition.

**SIGKILL and a `-timeout` expiry still leak**, and are worth knowing about
rather than being surprised by: there is no handler for the first, and on the
second the testing package panics the process itself, sending no signal and
running no cleanups. A leftover database is always named `apptest_` followed
by twelve hex digits, and dropping one is `DROP DATABASE "apptest_…"`.

## SSR is lenient by default, and that default is the interesting part

```go
apptest.New(t, …, apptest.WithStrictSSR())
```

A test has no Node renderer under its control: whether one answers depends on
whether somebody happens to be running `npm run dev` on this machine, and in
CI nothing is. Strict mode would therefore turn every page assertion into a
500 on one machine and a 200 on another — a suite that reports **where it ran**
rather than whether the code works.

So a test boot is lenient, and a test that wants to assert on rendering says
so. Pair `WithStrictSSR()` with `AssertServerRendered`, and be aware it needs
a renderer actually running.

**Run your suite both ways.** Moving `public/hot` aside for a full run is what
catches a test asserting on a string that only exists in a component — green
with a renderer up, red without one.

## A real connection, for a stream and an upgrade

`Send` drives `httptest.NewRecorder`, which is the right thing for almost
every test and cannot represent two kinds of request:

- **A stream.** `Send` returns when the handler returns, so an endpoint that
  holds its response open never returns at all. The test hangs until the
  binary times out rather than failing.
- **An upgrade.** A recorder does not implement `http.Hijacker`, so a
  WebSocket handshake fails on the hijack rather than on anything the test
  meant to exercise.

```go
server := a.Server()           // a real listener over the same handler
client := a.Client()           // shares the App's cookie jar

request, _ := http.NewRequest("GET", server.URL+"/broadcast/sse?channel=…", nil)
request.Header.Set(apptest.ActingAsHeader, "42")
response, err := client.Do(request)
```

`Server` is idempotent — a helper may ask for it without coordinating with
the test that already did — and it closes when the test ends.

**The shared cookie jar is the point, not a convenience.** An `EventSource`
and a browser `WebSocket` cannot set an `Authorization` header, so a cookie is
the only mechanism those endpoints have in production. The jar is mapped onto
the App's base URL, because a `httptest.Server` listens on a port the kernel
chose and cookies stored while driving the handler directly would otherwise
not be offered to it. One application in one test is one cookie identity
however the bytes reached it, so a sign-in through the request builder
authenticates a stream opened afterwards.

`Client` does not follow redirects: a stream endpoint answering 302 is a
failure the test should see.

## Escape hatches

```go
a.App()      // the booted app.App, to reach into the container
a.Handler()  // the http.Handler, to drive it directly
```

## Deliberate omissions

No parallel-safe containers, no HTTP recording, no snapshot testing. Model
factories are the application's own business — a factory that knows your
models belongs next to them.

go test ./...
